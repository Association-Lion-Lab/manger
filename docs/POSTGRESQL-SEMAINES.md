# PostgreSQL — semaines, déplacements et restes

25 octobre 2026 — tâche 11 en cours du [plan](MIGRATION-POSTGRESQL.md), après [les repas](POSTGRESQL-REPAS.md). SQLite reste normal, aucun schéma/transfert privé/déploiement/publication. Cette tranche porte les écritures de menus composés, copies, semaines types et restes ; suggestions/aperçus calculés et réponse agrégée GET /api/week restent à 12–13.

## Contrat et découpage

11a : règles pures de planification et méthodes dans les dépôts existants. Transactions PostgreSQL sous le verrou foyer `(1296125511,4)` avant toute lecture de référence/occupation/source/snapshot/capacité ; SQLite sous BEGIN IMMEDIATE synchrone, sans await pendant une transaction. Réutiliser l'enregistrement interne du repas ; aucune traduction SQL générique ni transaction imbriquée.

`POST /api/week/plan` : 1..14 repas maison ordinaires, dates dans les sept jours du début demandé, pas de doublon de créneau ni écrasement. Références/régimes et portions validés dans la transaction. Une recette commune sans affectations doit convenir au foyer entier, assiettes/affectations aux personnes choisies. Échec d'un élément = lot entier annulé, réponse `{added}` après COMMIT.

`POST /api/week/copy` : deux lundis distincts, comparaison exacte de sourceSnapshot avec JSON.stringify du DTO hebdomadaire courant sous verrou. Copies depuis semaines types : snapshot stocké, références actuelles revalidées à l'application, pas de réinterprétation des goûts. Aucun repas source vide ni reste dont le parent est hors snapshot ; liens locaux remappés vers les nouveaux IDs, y compris ID zéro. Source chronologique, identités/dates/liens internes vérifiés pour un snapshot ; aucune fusion de destination. Les quantités supplémentaires sont recalculées par les liens, pas copiées depuis extraPortions. Le snapshot porte le DTO de repas, pas une version de tous les ingrédients de recette.

Semaines types : nom trim 1..60 unités UTF-16, NUL refusé, unicité sensible à la casse, liste au tri SQLite NOCASE (pliage ASCII, pas lower Unicode). Date source lundi, snapshot JSON textuel conservé, id/createdAt/mealCount mêmes types ; 30 maximum sous verrou. Application vers un lundi, reprise atomique des repas et liens. Suppression d'un ID inconnu refusée ; IDs chiffres sûrs, zéro admis. Erreur JSON interne ou SQL privée en 503.

11b : déplacement/copie individuelle et création de restes dans les mêmes transactions. Déplacement : sourceDate/sourceSlot actuels requis, destination libre et chronologie avec parent/enfants revalidée ; garder ID et enfants. Copie : restes non copiables seuls, suppléments/assiettes conservés, références/régimes actuels validés. Pas de nouveau protocole de version : une édition du même ID au même créneau et une réutilisation d'ID SQLite ne sont pas distinguées par sourceDate/sourceSlot.

Restes : source maison cuisinée, pas elle-même des restes, recette commune non nulle ou plats distincts présents ; affectations seules sans recette refusées. Destination postérieure et libre ; sous-ensemble non vide d'assiettes nommées si source répartie, portions 1..20 chacune ; sinon 1..100 personnes. Recettes/protéines copiées depuis la source actuelle, pas depuis le corps reçu. Parent + tous ses restes, même hors semaine, limités à 100 portions ; deux ajouts concurrents recontrôlent la somme. Comme avant, pas de nouvelle exigence de régime sur des restes déjà préparés après édition d'un profil. Suppression/remplacement de source déjà protégés par 10 ; associations et titre repris, occasion regular et emplacement home.

11c : routes communes des sept opérations POST/DELETE et GET semaines types, mêmes statuts (200, 201, erreurs de saisie 400), corps 32 768 octets, panne interne 503 privée. Compte/origine et garde de restauration conservés ; aucune nouvelle page/heure/option client. Export ICS de 10 et wrappers nécessaires conservés ; supprimer seulement les branches SQL remplacées, sans extraire des fonctions voisines.

11d : contrats partagés SQLite/PostgreSQL réels, vieux tests semaines/restes conservés. Rollback après insertion/copie/remappage, concurrence de deux compositions/copies et de deux restes près de la limite, source ou référence modifiée pendant attente réelle, snapshots périmés, IDs zéro/grands, quotas/tri et erreurs privées HTTP. Agrégation, suite générale puis PostgreSQL successivement, modules/audit et suivi avant clôture. Examen externe toujours différé selon le choix utilisateur, relecture locale bornée ; pas de CLI externe.

Hypothèse à éprouver : tous les nouveaux écrivains respectant le verrou foyer préservent les liens et refusent un conflit sans lot partiel. Un SQL externe ignorant ce protocole n'est pas couvert. Le candidat partiel reste refusé au démarrage ; ces preuves locales ne valident ni le serveur Ubuntu ni Safari/Android ou Docker/Linux.

Sources de mise en œuvre : [client réservé node-postgres](https://node-postgres.com/features/transactions), [verrou transactionnel PostgreSQL](https://www.postgresql.org/docs/18/explicit-locking.html) et [reprises bornées de fs.rm](https://nodejs.org/docs/latest-v24.x/api/fs.html#fspromisesrmpath-options), uniquement pour le nettoyage des ressources de test.

## Preuves ciblées

Contrat commun des dépôts : composition, copies sans écrasement, snapshot périmé, modèles figés, unicité/tri ASCII/quota, suppléments conservés, sélection des restes depuis la source, chronologie, limites de capacité et source ID zéro. Le remappage fonctionne pour les copies et modèles ; les références extérieures à la semaine sont refusées. Régression de date 9999 reproduite puis corrigée avec lectures exactes par source/créneau, sans modifier globalement addDays.

Contrat HTTP commun protégé : mêmes réponses et statuts, body borné, compte/origine, pannes privées et IDs zéro/grands de modèles. Aucun appel SQLite derrière les routes PostgreSQL ; seul le hachage synthétique de la fixture est préparé via le helper SQLite mémoire, authentification et métier ensuite PostgreSQL. Les parcours non portés restent refusés, sans nouveau GET de liste ou de semaine agrégée.

Les tests natifs injectent une erreur après vraie mutation sur les deux moteurs (lot, remappage, application, restes, déplacement et modèles/retrait). PostgreSQL observe l'attente réelle avant changement de régime, snapshot, occupation et capacité ; une lecture pendant copie ne voit rien avant engagement, deux compositions/copies concurrentes ne laissent pas de mélange ni doublon. 21 tests réels ciblés passent, aucun ignoré ; anciens parcours HTTP SQLite et règles/rollback ciblés également verts. Trois cycles de relecture clos ; précision d'éligibilité et correction de date intégrées, aucun examen externe lancé.

La fixture PostgreSQL a reproduit EBUSY au retrait d'un dossier après arrêt de son cluster. Retrait seul repris de façon bornée par Node après les mêmes vérifications d'appartenance ; erreur persistante toujours bloquante, aucune requête SQL rejouée. Le même fichier repasse entièrement vert ; le dossier du premier échec a été retiré après vérification du chemin/marqueur et de l'arrêt. Les incidents non expliqués de 09 gardent leur statut inconnu. Les preuves globales et limites de clôture restent à compléter.
