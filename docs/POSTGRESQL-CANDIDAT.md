# Candidat PostgreSQL — étape 19 en cours

`postgres-app.js` ouvre les seuls dépôts PostgreSQL avec les secrets applicatifs. `db/readiness.js` contrôle rôle sans privilège/membre/propriété, version/état prêt, empreinte de structure et lecture effective des 22 tables des deux schémas. Aucune migration propriétaire au lancement web.

La page et les assets sont partagés avec SQLite par `public-http.js`, en conservant CSP, cache, icônes et code client. Tous les parcours métier passent par `protectAccounts`. Sauvegarde et restauration disponibles uniquement avec les contrôleurs implémentés ; copie de récupération dans `MANGER_DATA_DIR/recovery`. Les commandes locales de comptes utilisent la même configuration et les contrôles du candidat, sans secret propriétaire.

L’arrêt ferme les requêtes HTTP, puis les connexions ; les requêtes persistantes ont un délai de fermeture de cinq secondes. Les sous-processus de tests utilisent uniquement des fichiers, ports et bases temporaires synthétiques. Les validations natives et la relecture de 19a sont en cours. Aucun accès au serveur de l’utilisateur, aucune publication ou modification des volumes Compose existants.

Première relecture : CREATE/TEMP de base et accords directs sur catalogues/fonctions/paramètres système sont désormais refusés, en plus des rôles/appartenances/propriétés. Cela complète le préflight, sans audit exhaustif d’un cluster tiers : rôles neufs de bootstrap dédié restent obligatoires. Le répertoire de données est créé ou contrôlé avant écoute, parent préexistant, symlink et écriture groupe/autres refusés sur Unix. Port validé avant connexion et fermeture garantie en cas d’échec d’écoute. Le test d’arrêt direct observe HTTP suspendu puis sessions réellement retirées ; le sous-processus échoue si le secours SIGKILL est nécessaire. Sous Windows, SIGTERM termine le processus au niveau OS : la preuve de vidage vient du test direct, pas de ce signal.

Deuxième relecture : test natif raccordé à la commande PostgreSQL commune et à sa garde. Un TCP HTTPS sans ClientHello échappait à closeAllConnections : échec reproduit en test rouge à sept secondes, puis suivi des sockets dès connection et retrait à l’échéance de cinq secondes. Après fermeture HTTP et PostgreSQL, le point d’entrée termine explicitement le processus pour ne pas laisser un transport SMTP silencieux vivant ; close() du runtime seul garantit HTTP et PostgreSQL, pas la livraison d’un courriel. Le test SMTP utilise seulement un faux serveur loopback qui ne salue jamais, aucun message envoyé à un tiers. Contrôle des signaux Linux encore distinct de Windows.

Troisième et dernier cycle : nettoyage du faux serveur SMTP enregistré avant lancement et attente de contact bornée à cinq secondes. Les resets attendus du seul pair de test Windows sont traités explicitement ; un autre code d’erreur échoue toujours. Pas de quatrième cycle, pas d’outil externe.
