# Sauvegarde de l’instance complète — étape 18

Réalisation locale vérifiée, 26 octobre 2026. Étape 18a : archive et protections des outils ; 18b : restauration vers secours, contrôles et ouverture explicite. Aucun service utilisateur ni serveur Ubuntu manipulé. Le moteur normal reste SQLite.

Le bouton de sauvegarde du foyer exclut les accès. L’outil administrateur `postgres-instance.js` utilise les vrais pg_dump/pg_restore 18 et garde les 22 tables, les métadonnées de migration et les photos. Archive custom et manifeste privés dans un nouveau dossier exclusif, jamais d’écrasement. Un snapshot exporté partagé garde les données cohérentes ; le manifeste conserve seulement les empreintes/comptages, avec contrôle des métadonnées. Les compteurs de séquences ne sont pas figés par les snapshots PostgreSQL : leur égalité instantanée n’est pas promise, mais une prochaine identité sûre est exigée.

Les rôles globaux, mots de passe PostgreSQL, configuration et clés TLS sont sauvegardés séparément par l’exploitant. Même nom pour les deux rôles neufs sur la cible ; propriétaire séparé et non privilégié. Les ACL des objets sont conservées. Les droits de la base sont rétablis selon le modèle canonique Manger (PUBLIC exclu, application CONNECT uniquement), pas une copie de réglages personnalisés du cluster.

Les outils sont locaux et explicitement choisis par `MANGER_PG_TOOLS`. Sous Windows, DACL du nouveau dossier fixée avant tout secret ; sous Unix, 0700/0600. Le mot de passe passe par un fichier temporaire privé, jamais les arguments ou PGPASSWORD. Variables PG ambiantes supprimées, connexion libpq échappée comme une seule valeur ; CR/LF refusés. CA explicite exigée pour TLS distant, sans GSS ni certificat client implicite du profil. Désactivation TLS limitée à la boucle locale comme la frontière applicative. Délai du processus cinq minutes, snapshot inactif dix minutes.

La restauration SQL est strictement administrative : `--trusted-backup --target-empty --writers-stopped`. Une archive peut exécuter du SQL ; son empreinte n’établit pas son authenticité. N’utiliser qu’une archive propre de confiance. Vérification d’empreinte avant connexion, refus de cible occupée, révocation CONNECT engagée avant inventaire des autres connexions. Aucun utilisateur ordinaire connecté ne doit rester ; les autres écrivains administrateurs doivent être arrêtés par l’exploitant. Aucun arrêt forcé de connexion ni suppression d’objet utilisateur. Transaction unique pg_restore, sans clean/create. Comparaison exhaustive des données et métadonnées avant toute ouverture.

La cible restaurée reste fermée : `verify` est en lecture seule et `open --writers-stopped` refait les contrôles puis accorde CONNECT. Après perte de réponse, ne jamais rejouer restore : contrôler l’état, et ouvrir uniquement s’il correspond. Les écritures nouvelles rendent le manifeste ancien impropre à une nouvelle validation exacte ; il faut une nouvelle sauvegarde. Un échec laisse le dossier partiel privé et la cible fermée, sans annonce de rollback certain après la fin ambiguë d’un enfant.

Commandes depuis la racine, avec configuration administrative décrite dans [le transfert](POSTGRESQL-TRANSFERT.md) et `MANGER_PG_TOOLS` vers les binaires PostgreSQL 18 :

```sh
node postgres-instance.js backup /sauvegardes/privees/nouvelle-copie
node postgres-instance.js restore /sauvegardes/privees/nouvelle-copie --trusted-backup --target-empty --writers-stopped
node postgres-instance.js verify /sauvegardes/privees/nouvelle-copie
node postgres-instance.js open /sauvegardes/privees/nouvelle-copie --writers-stopped
```

Configurer la cible de secours avant restore, verify et open ; ne pas réutiliser par erreur la configuration de la source. Aucune de ces commandes ne provisionne le cluster ou les rôles. Ne pas les exécuter dans l’image applicative légère, qui n’embarque pas les outils PostgreSQL. Les exemples ne sont pas encore attestés sous Linux/Docker.

Sources : [pg_dump](https://www.postgresql.org/docs/18/app-pgdump.html), [pg_restore](https://www.postgresql.org/docs/18/app-pgrestore.html), [fichier de mots de passe](https://www.postgresql.org/docs/18/libpq-pgpass.html), [connexion libpq](https://www.postgresql.org/docs/18/libpq-connect.html). Première relecture de conception réconciliée : connexion littérale, DACL, CA explicite, isolation engagée, délai du snapshot, métadonnées et séquences, ACL de base et finalisation séparée. Validation finale détaillée ci-dessous.

Deuxième relecture : l’archive est copiée dans un espace privé puis hachée avant connexion et conservée ouverte pour pg_restore ; le chemin externe n’est plus rouvert après révocation. `open` exige une cible déjà fermée et refuse une source active sans changer CONNECT. `verify` distingue verified-closed et verified-open. Rôles, historique complet (versions/noms/checksums) et ACL de base sont revalidés ; privilèges d’un tiers refusés. Les horodatages des métadonnées sont hachés comme textes PostgreSQL UTC avec leur précision native, sans conversion Date JavaScript.

Les empreintes de lignes sont calculées par PostgreSQL, triées puis lues par curseur de mille petites empreintes ; Node ne charge pas toutes les photos pour le manifeste. Entiers exacts et paramètres de sérialisation explicitement fixés, algorithme versionné dans le manifeste. [SHA-256 natif PostgreSQL](https://www.postgresql.org/docs/18/functions-binarystring.html). Archive et manifeste sont synchronisés, ainsi que dossier/parent sur Unix. Les fichiers de sauvegarde restent non chiffrés, à conserver sur un stockage protégé.

Un test initial a montré que pg_dump omet les ACL explicites équivalentes aux droits par défaut : la structure restaurée était sémantiquement identique mais son empreinte stricte différait. Les permissions canoniques existantes sont maintenant réappliquées avec CONNECT maintenu fermé avant comparaison ; aucun contrôle d’empreinte n’est affaibli. Le test de connexion concurrente retient explicitement son client, au lieu de supposer qu’un pool inactif reste connecté.

Troisième et dernier cycle de relecture : validation de tout le manifeste ajoutée avant connexion (algorithme, 22 noms exacts, comptages et toutes les empreintes). Le test utilise une adresse volontairement impossible et exige le refus de format avant toute connexion ; il confirme également la cible toujours vide et son ACL inchangée. Aucun quatrième cycle ou outil externe. La cible de secours doit déjà respecter le modèle de rôles et ne donner aucun droit à PUBLIC ou à un tiers sur sa base ; une base neuve laissée avec les droits publics PostgreSQL par défaut est refusée. Le provisionnement vient à l’étape 19.

Preuves ciblées : vrais pg_dump et pg_restore sur deux clusters privés ; toutes les valeurs des 22 tables et les photos comparées après récupération, métadonnées à la microseconde contrôlées, historique altéré et ACL tierce refusés, vraie connexion HTTP avec le mot de passe restauré et session préexistante reconnue. Commande verify exécutée en sous-processus, rapport sans contenu privé ; création après reprise avec identité sûre. Aucun test de restauration à partir d’une base personnelle. La vérification Linux/Docker et l’exécution sur le serveur de l’utilisateur restent distinctes.

26 octobre 2026 : étapes 01–18 closes, cinq restantes ; prochaine 19, candidat et vérification Docker. 404 tests généraux et 231 PostgreSQL réels réussis, aucun ignoré, HTTPS inclus ; 27 fichiers et 29 parents PostgreSQL. Vrais pg_dump/pg_restore sur deux clusters privés, reconnexion HTTP avec compte restauré et commande verify exécutée. Trois cycles de relecture réconciliés, dernier défaut de manifeste corrigé et testé avant connexion. Modules/image contrôlés sans Docker. Aucun serveur personnel, donnée réelle, bascule ou publication.
