# Schéma PostgreSQL en préparation

22 octobre 2026 — tranche 03b du [plan validé](MIGRATION-POSTGRESQL.md). **L'application utilise encore SQLite.** Le schéma cible est testé sur un PostgreSQL local jetable, sans import utilisateur, amorçage de recettes/comptes, changement de Compose ou connexion au serveur personnel.

## Organisation et types

`db/migrations/001-initial.js` décrit la version PostgreSQL **1**, distincte du numéro SQLite 4. Les 18 tables du foyer sont dans `household`, les quatre tables d'accès dans `auth` : [inventaire des colonnes et consommateurs](POSTGRESQL-CONTRATS.md). Un troisième schéma technique privé, `manger_meta`, contient seulement `schema_migrations(version,name,checksum,applied_at)` ; il ne fait pas partie des données métier à reprendre.

| Donnée | Choix cible et conséquence |
| --- | --- |
| Identifiants | `bigint GENERATED BY DEFAULT AS IDENTITY` pour conserver les IDs importés ; limite de séquence et `CHECK` des valeurs explicites dans l'intervalle des entiers sûrs JavaScript. Le pilote retourne encore les `bigint` en chaînes : conversions API explicites à faire en 04 et dans chaque parcours, pas de parseur global lossy. |
| Quantités et drapeaux | `double precision`, sans arrondi ajouté ; refus SQL des quantités non finies. Drapeaux `smallint` bornés à 0/1 pour garder la représentation stockée actuelle. Le contrôle positif n'est pas ajouté à `shopping_manual.amount`, qui ne l'avait pas dans SQLite. Les valeurs source hors domaine seront signalées au précontrôle, pas nettoyées silencieusement. |
| Textes, jours et JSON | `text COLLATE "C"` pour les comparaisons binaires ; clés de jour et instants déjà encodés conservés en texte, sans conversion de fuseau ; goûts et snapshots JSON gardés tels quels. Pas de refonte JSONB. Expirations d'accès en millisecondes `bigint`, hachages conservés, jamais régénérés par le DDL. |
| Photos et placard | `bytea` pour les photos et `pantry.food_key` : conserve notamment l'octet zéro de la clé opaque. Conversion Buffer/UTF-8 aux frontières du futur dépôt de données. |
| Ordre des rayons | `shopping_aisles.sort_order`, identité entière sûre `NOT NULL UNIQUE`, pour reprendre le `rowid` historique sans dépendre de l'ordre physique. Une mise à jour du rayon ne change pas cet ordre. Recalage de la séquence après import à réaliser avec l'outil opérateur. |

Les FK, clés composées, unicités et contraintes existantes sont conservées : cascade des enfants de recettes/personnes/repas, `SET NULL` de la recette directement planifiée, recette d'une assiette protégée, source de restes `RESTRICT`, invitation courante `id=1`, suppression de compte avec session en cascade et créateur d'invitation protégé. Cela ne remplace pas les validations métier et la concurrence des futurs parcours.

## Exécution explicite et versionnement

`migrateSchema(migrationPool, applicationRole)` de `db/postgres-schema.js` est une opération administrative interne, **pas une route ou une commande de déploiement prête à utiliser**. Le pool doit viser une base dédiée et être connecté en propriétaire de migration non-superutilisateur ; le rôle applicatif séparé doit exister. Importer le module n'ouvre aucune connexion et ne charge même pas le pilote `pg`.

1. Valider le nom de rôle avant toute connexion, réserver un client et ouvrir une transaction **READ COMMITTED explicite**. Fixer le `search_path` à `pg_catalog`, un délai de verrou de 5 secondes et de requête serveur de 15 secondes. Les délais client du pool restent aussi applicables ; dans la fixture actuelle, le pilote peut donc interrompre avant le délai serveur.
2. Acquérir le verrou transactionnel commun `(1296125511,1)` **avant** de lire/créer l'historique. Une seconde initialisation attend ; son nouvel instantané voit ensuite le résultat de la première, même si la connexion utilisait par défaut `repeatable read`.
3. Vérifier séparation/propriété/attributs/appartenances des rôles. Sans historique, refuser les schémas utilisateurs ou objets publics préexistants : contrôle des dépendances de namespace dans `pg_depend`, couvrant aussi une collation et pas seulement des tables. Ne pas effacer une cible non reconnue pour la rendre compatible.
4. Exiger un préfixe exact de la liste statique des migrations : version, nom et SHA-256 du SQL final. Historique déjà créé mais vide, modifié ou plus récent = refus. Exécuter DDL et insertion de version dans la même transaction, puis appliquer les permissions avant `COMMIT`.
5. En échec, tenter `ROLLBACK`, conserver les deux causes si le rollback échoue et détruire la connexion en erreur ; toujours libérer le client réservé. Aucun repli SQLite ni seconde tentative automatique. Une réponse de commit perdue reste un résultat incertain : vérifier l'historique avant toute décision opérateur.

Les migrations de la liste sont du code du dépôt de confiance, jamais du SQL chargé depuis un navigateur ou un fichier utilisateur. Après usage, ne pas modifier un SQL déjà appliqué : créer une nouvelle version et l'ajouter explicitement à la liste. Le contrôle d'empreinte n'est **pas** un audit exhaustif de dérive manuelle des tables après migration ; la santé et les contrats des futurs parcours devront aussi vérifier le schéma dont ils dépendent.

## Droits et limites de confiance

Le rôle applicatif reçoit `USAGE` sur `household/auth`, CRUD sur leurs tables et `USAGE` des séquences. Il n'est propriétaire ni de la base ni des objets, n'a aucune appartenance de rôle et ne peut modifier l'historique. Droits publics et droits explicites antérieurs sur les objets ciblés sont retirés avant les accords minimaux ; des privilèges par défaut volontairement trop permissifs font partie des tests. Pas de création de schéma/table/objet temporaire, `ALTER`, `DROP`, `TRUNCATE`, `SET ROLE` vers le propriétaire ou `setval` pour l'application.

**Précondition d'exploitation :** les rôles de test sont neufs et créés par le bootstrap contrôlé. Le préflight n'est pas un auditeur de toutes les ACL globales d'un cluster arbitraire : un administrateur pourrait avoir accordé des droits de paramètres ou de fonctions système à un ancien rôle. Le futur provisionnement en 19 doit créer/vérifier des rôles dédiés sans ces accords, pas recycler un rôle de confiance inconnue. Aucun droit global n'est accordé par le code actuel ; aucun superutilisateur ne sert aux tests métier. Un administrateur PostgreSQL capable de changer le cluster reste dans la frontière de confiance.

Le recalage de séquences est une autorité **opérateur**, distincte de l'usage courant. `setval` ne se rollbacke pas comme les lignes ; ne pas accorder `UPDATE` des séquences à l'application pour contourner ce point. Les tâches 15–17 doivent définir et tester une voie administrative contrôlée pour l'import et la restauration guidée, sans supprimer le bouton de restauration, exposer un mot de passe propriétaire au client ou faire une bascule SQLite automatique. Ce lot ne livre ni import, ni restauration PostgreSQL, ni downgrade destructif ; un DDL initial en échec est annulé transactionnellement. Une cible contenant des données utiles ne doit jamais être supprimée pour revenir à zéro.

## Preuves et suite

Contrôle sans connexion : `node --test postgres-schema.test.js`, deux tests. Intégration réelle : `node --test test-support/postgres-schema.integration.cjs`, **10 tests réussis, aucun ignoré**. Le test compare noms/colonnes des 22 tables à des schémas SQLite ouverts exclusivement en mémoire, puis vérifie les données synthétiques et contraintes : zéro amorçage, grands IDs, précision, NUL/photos/Unicode, tri binaire, ordre des rayons, FK et droits. Le refus d'une cible avec table ou collation conserve l'existant.

Deux migrations réellement bloquées simultanément en base ne produisent qu'une version appliquée. Un échec injecté **après le DDL réel** annule aussi `household/auth/manger_meta`, puis la reprise réussit. Versions/nom/empreinte invalides refusés sans perdre les données ; arrêt/reprise du serveur puis seconde exécution sans migration rejouée. Une mutation désactivant le contrôle de checksum **en mémoire seulement** fait échouer le test attendu, sans modifier la source.

La première attente du test de restes utilisait `23503` ; PostgreSQL 18 renvoie ici `23001` (`restrict_violation`), confirmé dans les codes officiels et attendu désormais explicitement. La contrainte n'a pas été changée pour satisfaire le test. Suite générale : **229 réussites, aucune ignorée**, HTTPS inclus ; `node image-check.js` réussi. Pas de validation Docker/Linux, Ubuntu ou téléphone, ni de données réelles lues ou migrées.

Dernière sous-tranche de 03 réalisée : `npm run test:postgres` agrège maintenant la fixture et le schéma, **18 tests réussis, aucun ignoré** ; les fichiers `.integration.cjs` ne sont pas découverts par la suite générale par défaut. La garde de commande a échoué avant son élargissement puis passe avec la nouvelle commande. Tous les clusters temporaires ont été retirés à la fin ; outils de test conservés dans le cache ignoré. Tâche 03 close, frontière asynchrone applicative en tâche 04.

Commande commune aussi vérifiée avec `MANGER_TEST_PG_BIN` pointant vers un chemin inexistant : les deux suites échouent explicitement, code 1 et zéro test ignoré, avant création de cluster. Aucun passage vert artificiel en l'absence de PostgreSQL.
